# 연금플러스 MVP 개발환경·협업 가이드

| 항목 | 내용 |
|---|---|
| 목적 | 세 명이 같은 환경에서 기능을 나눠 개발하고 안전하게 통합하기 위한 기준 |
| 적용 기간 | 4일 MVP 개발 기간 |
| 기준 프로토타입 | `docs/01-product/예상_프로토타입.html` |
| 관련 계획 | `docs/00-start/간단_실행계획.md` |
| 디자인 기준 | `docs/03-design/design-system/연금플러스 디자인 시스템.dc.html` |
| 디자인 구현 기준 | `docs/03-design/디자인시스템_개발적용가이드.md` |

> 이 문서는 모든 팀원이 공통으로 사용한다. 저장소를 처음 받은 사람도 아래 순서대로 진행하면 설치, 실행, 개인 브랜치 생성과 작업 제출까지 할 수 있어야 한다.

## 시작 순서 요약

모든 팀원은 개발 시작 전에 아래 항목을 순서대로 완료한다.

1. Node.js 24 LTS, Git, Visual Studio Code를 설치한다.
2. GitHub 저장소 초대를 수락한다.
3. 저장소를 clone한다.
4. `npm install`을 실행한다.
5. `npm run dev`로 화면이 열리는지 확인한다.
6. 자신의 `work/<이름>` 브랜치를 만든다.
7. 담당 기능을 코딩 에이전트에게 한 작업씩 요청한다.
8. 브라우저 확인과 빌드 확인 후 `dev`로 PR을 만든다.

## 1. 기술 구성

### 최종 권장 구성

- Vite
- React
- TypeScript
- Tailwind CSS
- React Router
- Lucide React
- Vitest
- Vercel

### 사용하지 않는 것

- Next.js
- Supabase와 데이터베이스
- 실제 계정 생성·본인 인증·비밀번호 찾기
- 백엔드 API
- Redux·Zustand 등 별도 상태 관리 도구
- Recharts
- shadcn/ui 대량 설치

### 선택 이유

기준 프로토타입은 단일 HTML 안에서 9개 화면, 모달, 탭, 상태 전환과 계산을 실행하는 클라이언트형 앱이다. 서버 렌더링, 검색 노출, 데이터베이스가 필요한 구조가 아니므로 Next.js보다 Vite React가 단순하다.

기존 프로토타입에서 재사용할 것은 화면 내용, 사용자 흐름, 샘플 데이터와 동작 규칙이다. 117KB 규모의 HTML 전체를 그대로 React에 붙이지 않고 기능별 컴포넌트로 나눈다.

세 명 모두 아래 도구를 동일하게 설치한다.

| 도구 | 기준 | 용도 |

모든 팀원은 Node.js 24 LTS로 버전을 통일한다. 설치 후 VS Code 터미널에서 아래 명령으로 확인한다.

```bash
node --version
npm --version
git --version
```

Node.js가 `v24`로 시작하지 않으면 작업을 시작하지 않고 버전을 먼저 맞춘다. Windows PowerShell에서 npm 실행 정책 오류가 발생하면 VS Code 터미널 프로필을 `Command Prompt`로 변경한다.

### VS Code 권장 확장

- ESLint
- Prettier - Code formatter
- Tailwind CSS IntelliSense

확장 프로그램은 위 세 개만 공통으로 맞춘다. 개인 편의 확장은 자유롭게 사용하되 프로젝트 설정 파일은 임의로 변경하지 않는다.

## 3. 공통 저장소 준비

### 프로젝트 초기 구성 담당만 실행

프로젝트 초기 구성 담당자가 저장소에서 한 번만 수행한다. 다른 팀원은 아래 생성 명령을 실행하지 않는다.

```bash
npm create vite@latest . -- --template react-ts
npm install
npm install react-router lucide-react
npm install -D tailwindcss @tailwindcss/vite vitest
```

설정이 완료된 뒤 아래 명령이 모두 성공해야 한다.

```bash
npm run dev
npm run build
npm run test
```

React Router는 가장 단순한 Declarative Mode의 `BrowserRouter`, `Routes`, `Route`만 사용한다. loader, action, SSR, React Router Framework Mode는 이번 MVP에서 사용하지 않는다.

Vercel에서 하위 URL을 직접 열거나 새로고침할 때 발생하는 404를 막기 위해 프로젝트 루트에 `vercel.json`을 추가한다.

```json
{
  "$schema": "https://openapi.vercel.sh/vercel.json",
  "rewrites": [
    {
      "source": "/(.*)",
      "destination": "/index.html"
    }
  ]
}
```

### 모든 팀원이 실행

GitHub 저장소를 clone한 뒤 각자 아래 명령을 실행한다.

```bash
git clone <저장소 주소>
cd pension-plus
npm install
npm run dev
```

터미널에 표시된 로컬 주소를 브라우저에서 열어 화면이 나타나는지 확인한다. 문제가 있으면 작업을 진행하기 전에 팀 채널에 오류 화면과 터미널 메시지를 공유한다.

패키지를 새로 설치해야 할 때는 팀 채널에 먼저 공유하고 프로젝트 초기 구성 담당자가 반영한다. 같은 목적의 라이브러리를 중복으로 추가하지 않는다.

## 3.1 바이브코딩 작업 방식

세 명 모두 코드를 처음부터 직접 작성하기보다 코딩 에이전트에게 작고 명확한 작업을 맡기고 결과를 실행해 확인한다. 에이전트에게 한 번에 전체 서비스를 만들어 달라고 요청하지 않는다.

### 한 작업의 표준 순서

1. 개인 작업 브랜치로 이동한다.
2. 에이전트에게 담당 범위와 수정 가능한 폴더를 알려준다.
3. 먼저 관련 파일을 읽고 짧은 구현 계획을 제시하게 한다.
4. 한 화면 또는 한 계산 함수만 구현하게 한다.
5. 에이전트에게 빌드와 테스트를 실행하게 한다.
6. 팀원이 브라우저에서 직접 화면과 숫자를 확인한다.
7. 문제가 없으면 커밋과 PR을 만든다.

### 공통 프롬프트 템플릿

```text
연금플러스 4일 MVP 작업입니다.

먼저 루트의 AGENTS.md와 아래 문서를 읽어주세요.
- docs/00-start/개발전_준비.md
- docs/02-development/개발환경_협업가이드.md
- docs/03-design/디자인시스템_개발적용가이드.md

이번 작업: [한 문장으로 작성]
수정 가능한 폴더: [담당 폴더]
수정하면 안 되는 폴더: [다른 담당 폴더]
완료 조건:
1. [화면 또는 동작]
2. [예외 또는 표시]
3. npm run build 성공

먼저 관련 파일을 확인하고 5단계 이내의 구현 계획을 제시한 뒤 작업하세요.
작업 후 변경 파일, 확인 방법, 남은 문제를 알려주세요.
```

### 기능1 요청 예시

```text
이번 작업은 /transfer/status 이관 현황판 구현입니다.
수정 가능한 폴더는 src/features/transfer뿐입니다.
5단계 타임라인, 현재 단계 강조, 예상 완료 기간, 제한 업무를 표시하세요.
시연용 mock 데이터만 사용하고 실제 금융기관 연동은 만들지 마세요.
```

### 기능2 요청 예시

```text
이번 작업은 /withdrawal/result 인출 결과 화면 구현입니다.
수정 가능한 폴더는 src/features/withdrawal/components와 pages입니다.
calculator.ts는 수정하지 말고 반환값을 사용하세요.
3단계 차감액, 총 예상 세금, 실수령액, 모의계산 문구를 표시하세요.
```

### 에이전트 결과를 그대로 병합하지 않는 기준

- 요청하지 않은 패키지를 설치했다.
- 다른 담당 폴더를 대량 수정했다.
- 계산식을 화면 컴포넌트 안에 새로 만들었다.
- 빌드 또는 테스트를 실행하지 않았다.
- mock 데이터인데 실제 계좌 정보처럼 표현했다.
- 기존 화면을 이유 없이 삭제하거나 전체 구조를 바꿨다.

이 경우 병합하지 않고 에이전트에게 범위를 좁혀 수정하도록 요청한다.

## 4. 폴더 구조와 소유권

```text
src/
├─ app/
│  ├─ App.tsx
│  └─ router.tsx
├─ components/
│  └─ ui/
├─ features/
│  ├─ transfer/
│  │  ├─ components/
│  │  ├─ pages/
│  │  ├─ mock.ts
│  │  └─ types.ts
│  └─ withdrawal/
│     ├─ components/
│     ├─ pages/
│     ├─ calculator.ts
│     ├─ calculator.test.ts
│     ├─ mock.ts
│     └─ types.ts
├─ lib/
│  ├─ format.ts
│  └─ constants.ts
├─ styles/
│  └─ globals.css
└─ main.tsx
```

### 파일 담당 원칙

- 기반/계산 역할: `app`, `lib`, 기능2의 `calculator`와 테스트
- 기능1 역할: `features/transfer` 전체
- 기능2 UI 역할: 기능2의 `components`, `pages`, `mock`
- `components/ui`와 공통 설정 파일은 수정 전에 팀에 공유
- 다른 담당 폴더의 오류를 발견하면 직접 대규모 수정하지 않고 담당자에게 전달

킥오프에서 세 역할에 팀원 이름을 배정하고, 담당 폴더를 팀 채널 상단에 고정한다.

## 5. 화면 경로

| 경로 | 화면 | 담당 영역 |
|---|---|---|
| `/login` | 로그인 — 시연용 UI | 기반/계산 |
| `/signup` | 회원가입 — 시연용 UI | 기반/계산 |
| `/` | 홈 | 기반/계산 |
| `/transfer/check` | 이전 계좌·종목 확인 | 기능1 |
| `/transfer/confirm` | 잠금 기간·최종 확인 | 기능1 |
| `/transfer/status` | 이관 현황판 | 기능1 |
| `/withdrawal` | 인출 조건 입력 | 기능2 UI |
| `/withdrawal/result` | 인출순서·세금 결과 | 기능2 UI |

경로는 위 목록으로 고정한다. 새로운 화면이 필요하면 먼저 기존 화면의 모달·탭·아코디언으로 처리할 수 있는지 확인한다.

로그인·회원가입은 강의 제출 요건을 보여주기 위한 mock 화면이다. 입력값을 서버로 보내거나 계정을 생성하지 않으며, 로그인 버튼은 시연 흐름으로 홈에 이동한다. 두 화면 모두 `시연용 화면 · 실제 계정이 생성되지 않습니다`를 표시한다.

## 6. GitHub 브랜치 구성

### 브랜치

```text
main             최종 시연 가능한 안정 버전
dev              세 사람의 작업을 합치는 통합 버전
work/<이름>      각 팀원의 개인 작업 브랜치
```

예시:

```text
work/donggeon
work/goeun
work/seungyeon
```

개인 브랜치 이름은 영문 소문자로 작성한다. 역할이 바뀌더라도 브랜치 이름은 그대로 유지한다.

### 브랜치 규칙

- `main`과 `dev`에는 직접 push하지 않는다.
- 각자 `work/<이름>` 브랜치에서만 작업한다.
- 작업을 합칠 때 `work/<이름>`에서 `dev`로 PR을 만든다.
- `dev`에서 전체 기능을 확인한 뒤에만 `main`으로 병합한다.
- 최종 배포는 `main`을 기준으로 한다.

### 작업 시작

저장소를 이미 clone했다면 최초 한 번:

```bash
git switch dev
git pull origin dev
git switch -c work/<이름>
```

매일 작업 시작 전:

```bash
git switch dev
git pull origin dev
git switch work/<이름>
git merge dev
```

충돌이 발생하면 임의로 파일을 삭제하지 않고 해당 파일 담당자와 함께 해결한다.

### 작업 종료 후 PR 제출

```bash
git status
git add <변경한 파일>
git commit -m "feat: 작업 내용"
git push -u origin work/<이름>
```

GitHub에서 `work/<이름>` → `dev` 방향으로 PR을 만든다. `main` 방향으로 바로 만들지 않는다.

## 7. 커밋과 PR 규칙

### 커밋 메시지

다음 형식을 사용한다.

```text
feat: 이관 현황 타임라인 구현
fix: 인출 한도 초과 계산 수정
style: 결과 카드 간격 조정
test: 인출 계산 경계값 추가
docs: 실행 방법 업데이트
```

한 커밋에는 한 가지 목적의 변경만 담는다. 하루 작업 전체를 한 번에 커밋하지 않는다.

### PR 제목

```text
[기능1] 이전 계좌 확인 화면
[기능1] 이관 현황 상태 추가
[기능2] 인출 조건 입력 화면
[계산] 연금수령한도 계산
[공통] 라우팅과 레이아웃
```

### PR 본문

```markdown
## 구현한 것
- 

## 확인 방법
1. 

## 남은 문제
- 없음
```

### 병합 조건

- `npm run build` 성공
- 담당 화면 직접 확인
- PR 확인 방법 작성
- 다른 팀원 한 명 확인
- 충돌이 없는 상태

## 8. 하루 통합 방식

| 시점 | 할 일 |
|---|---|
| 오전 시작 | `dev`의 최신 변경을 개인 브랜치에 병합 |
| 오후 중간 | 완성된 작은 단위가 있으면 첫 PR |
| 종료 1시간 전 | 당일 작업 PR 제출 |
| 종료 30분 전 | `dev`에서 두 기능 연결과 빌드 확인 |

큰 기능을 3일 동안 개인 브랜치에만 보관하지 않는다. 완성된 화면이나 계산 함수부터 작은 PR로 매일 통합한다.

## 9. 코드 작성 규칙

- 한 파일이 300줄을 크게 넘으면 컴포넌트 또는 함수로 분리한다.
- 화면에 금액을 직접 문자열로 반복 작성하지 않고 mock 데이터에서 가져온다.
- 계산식은 React 컴포넌트 안에 작성하지 않는다.
- 세율과 기준값은 `constants.ts`에서 관리한다.
- 공통 금액 표시는 `format.ts`를 사용한다.
- `any` 타입은 사용하지 않는다.
- 사용하지 않는 코드와 주석 처리된 코드는 병합 전에 제거한다.
- 모든 모의 화면에는 `시연용 데이터` 또는 `모의계산` 표시를 둔다.

## 10. 프로토타입 이전 기준

`docs/01-product/예상_프로토타입.html`에는 다음 흐름이 이미 구현돼 있다.
