## 1. 서론

### 1.1 목적

본 문서는 KB증권 **일반 고객(PB 미배정)** 을 대상으로 한 두 가지 기능 — **기능1 이수관 현황판**과 **기능2 인출순서 시뮬레이터** — 의 소프트웨어 요구사항을 정의한다.

이관 처리 속도는 원 사업자와 예탁결제원 단일 인프라에 묶여 있어 어느 증권사도 단축할 수 없다. 경쟁축은 **처리 속도가 아니라 그 상태를 고객 눈에 보이게 하는가**로 이동했다. PB가 배정된 고액 자산가는 상담사를 통해 진행 상황·세제 설명을 받지만, 일반 고객 구간에는 이 기능이 시스템화되어 있지 않다. 본 시스템은 사람(PB·콜센터)이 수행하던 확인·설명을 화면으로 대체하여 비대면 원가를 낮추고 이관 물량 이탈을 방어하는 것을 목적으로 한다.

**Problem Statement** — KB증권의 일반 고객은 연금 이전을 결심한 순간 상품별 이전 가능 여부, 실시간 진행 현황, 추가 운용지시 제한 사유를 즉각 확인할 방법이 없어 투자손실을 최소화하며 이관을 완료하는 것을 달성하지 못하고 있다.

## 3. 시스템 맥락 및 인터페이스

**클라이언트**
- KB증권 앱 (모바일) — 기능1·기능2 전 화면

**내부 서비스 (기능 단위)**
- 이수관 현황판 서비스 — 진행 단계 상태 관리, 완료일 밴드 산정, 매매 잠금 계층(`trading_window`) 관리
- 인출순서 시뮬레이터 서비스 — 연금수령한도 산식, 3층 인출순서 계산, 세율 적용
- 알림 서비스 — 접수완료/의사확인 예정/자산정리 착수 알림, 잔고 반영 알림(60초 이내)
- 세율표 관리 서비스 — 시행일 기반 세율·감면율 설정, 최종 갱신일 노출, 갱신 지연 시 결과 차단

| 마이데이터 (연금 API: `DB-001`, `DC-001~004`, `IRP-001~004`) | In | 계좌잔액·평가금액·개설일·거래내역 등 | 확정 |

## 4. 구체적 요구사항

### 4.1 기능 요구사항

우선순위는 PRD의 MoSCoW(Must/Should/Could) 표기를 그대로 유지한다. 인수기준(AC)은 PRD §5·§6 원문의 핵심만 요약했으며, 전문은 원본 PRD를 참조한다.

- KB증권은 "거래내역이 없는 신연금저축계좌로만 이체 가능"이라는 제약이 있어, 가입일 승계의 법정 단서 요건(시행령 §40의4④ 단서, 신규 설정 + 전액 이체)이 항상 충족되는 것으로 가정한다. 다만 원장이 실제로 승계를 적용하는지는 §14.1의 착수 전 확인 대상이다.
- 프로토타입 F1-03(예약·잠금 구간 미리보기)은 예외적으로 종목이 있는 사례(서동현 IRP 이체, 6종·48,500,000원)를 사용하며, 나머지 화면은 연금저축보험 이체(종목 없음) 사례를 사용한다.

## 7. 부록

### 7.1 계산 규칙 (PRD §7 원문 근거)

**연금수령한도 (소득세법 시행령 §40의2)**

```
연금수령한도 = 과세기간 개시일 현재 평가액 ÷ (11 − 연금수령연차) × 120 / 100
잔여 한도   = 연금수령한도 − 당해 과세기간 기인출액
```

- 11년차 이상: 산식 미적용(한도 없음)
- 2013.3.1 이전 가입: 6년차부터 기산
- 승계 계좌: 피상속인의 연금수령연차를 승계
- 한도 초과분: 연금외수령으로 간주
- 부득이한 인출(§20의2①)은 '인출한 금액'에 포함하지 않음

**인출순서 (소득세법 시행령 §40의3①)**

| 순위 | 재원 | 세금 |
|---|---|---|
| 1 | 과세제외금액 | 비과세 |
| 2 | 이연퇴직소득 | 퇴직소득세 × 70/60/50%(감면), 한도 초과 시 100% |
| 3 | 세액공제분·운용수익 등 | 연금소득세 3.3~5.5%, 한도 초과 시 기타소득세 16.5% |

1층 내부 순서: ① 당해 과세기간 납입 연금보험료 → ② 당해 과세기간 전환금액 → ③ 세액공제 한도초과 납입액 → ④ 세액공제 미수령 납입액(공제확인서 제출로 확인되는 날부터 과세제외금액으로 전환, §40의3② 단서·§201조의10). 운용손실은 인출순서의 **역순**으로 차감된 후의 금액을 기준으로 한다(§40의3⑤).

**세율 (2026.1.1 시행 기준, 지방소득세 포함 실효세율)**

| 구분 | 실효세율 |
|---|---|
| 연금소득세 (55~69세) | 5.5% |
| 연금소득세 (70~79세) | 4.4% |
| 연금소득세 (80세 이상) | 3.3% |
| 종신형 수령 (2026.1.1 인하) | 3.3% |

### 7.2 상태·데이터 모델

**핵심 엔터티**

| 엔터티 | 필드(안) |
|---|---|
| `TRANSFER` | `transfer_id`, `transfer_status`, `route`, `submitted_at`, `settled_at`, `critical_path_holding` |
| `HOLDING` | `code`, `holding_status`, `eval_amount`, `realized_pl`, `settle_days`, `is_critical_path`, `layer`(확정/추정) |
| `LOCK_WINDOW` | `start_at`, `end_band_from`, `end_band_to`, `business_days_min`, `business_days_max`, `confidence` |
| `TRADING_WINDOW` | `value`, `buy_allowed`, `sell_allowed`, `pay_allowed`, `claim_allowed`, `confidence` |
| `withdrawal_request` | `account_type`, `withdrawal_amount`, `tax_bucket_breakdown[]` |
| `tax_bucket_breakdown` | `bucket_type`, `amount`, `tax_rate`, `layer` |
| `pension_limit_input` | `eval_amount`, `payment_year`, `age`, `has_retirement_fund` |

**설계 규칙** — ① 모든 추정 필드에 `layer`+`confidence` 부여 ② 날짜는 단일값이 아니라 밴드로 저장 ③ `critical_path_holding`은 서버가 지정(프런트 계산 금지) ④ `trading_window`는 `confidence`가 낮으면 `LOCKED`로 내려 쓴다(REQ-NF-015와 직결).

**상태값 Enum**

```
transfer_status  = DRAFT | RECEIVED | REQUESTED | VERIFYING | LIQUIDATING
                  | REMITTING | COMPLETED
                  | ACTION_REQUIRED | REJECTED | PARTIAL_BLOCKED | DELAYED
holding_status   = 실물이전 가능 | 현금화 필요 | 판정 불가  (+ is_critical_path)
trading_window   = OPEN | SELL_ONLY | LOCKED | REOPENED
```

`ACTION_REQUIRED`가 실질적으로 가장 중요하다 — ③ 병목의 상당 부분이 "고객이 이관사 전화를 모르는 번호로 받지 않아서" 발생하며, 이는 고객이 해결할 수 있는 유일한 구간이다.

**마이데이터의 한계 (연금 API 범위: 은행/금융투자 업권)**

- 제공됨: 계좌잔액, 평가금액, 투자원금, 개설일, 최초납입일, 만기일, 금리, 누적금액, 사용자부담금, 가입자부담금, 상품별 원금·좌수·만기, 거래내역
- 제공 안 됨: 과세제외금액 / 이연퇴직소득 / 세액공제 받은 납입액 (양 업권 규격 모두 부재)
- 결론: **한도 계산은 마이데이터로 타사 계좌까지 가능**(평가액·개설일만 필요), **세액 계산은 마이데이터만으로 불가**(자사 계좌 전용 설계, REQ-FUNC-046)

### 7.4 릴리스 계획 (요약)

| 단계 | 범위 | 승격 조건 |

| 0. 내부 | 임직원 IRP 이관 건(기능1)·세율표 검증(기능2)·콜센터 문의 코드 태깅 | 문의율 기준선 산출 가능·AC 전건 통과 |
| 1. 제한 베타 | PB 미배정·IRP 단건 10%(기능1) / 기능2 전 사용자 공개 | 밴드 적중률 ≥ 75%·주문 거부율 ≤ 0.1%·계산 오류 0건 |

기능2는 시행령 조문 기반이라 외부 연동 없이 구현 가능하지만, REQ-FUNC-034(가입일 확정 카드 → 기능2 연동, 두 화면 가입일 불일치 시 실패)에 따라 기능1이 확정한 가입일 값을 그대로 이어받는다. 이 정합성 요구 때문에 기능2의 착수는 기능1의 완료를 전제로 하며, 두 기능은 함께 출시한다(PLAN-PENSIONPLUS-MVP-001 §4.1, 2026-08-25 결정).

### 7.6 착수 전 확인 사항 (원본 PRD §14 요약)

**연금시스템팀 대상** — 가입일 승계 기준(종전/신규), 라목 잔액 별도 관리 여부, KB증권 상품별 결제 규정 실측 가능 여부, 의사확인 자동취소 기준일(1영업일 vs 5영업일), 이연퇴직소득 입금일 원장 기록 여부, 전문 수신 시각의 이관사×자산구성 단위 적재 가능 여부, 콜센터 문의 코드 분류 추가 가능 여부, 전송 후 매도 허용 여부(`trading_window` 값 확정), 예약 저장 구조와 이체 신청 접수 규정 충돌 여부.

**법무·컴플라이언스 대상** — 이 계산이 투자자문업에 해당하는지, 타사 계좌 조회에 필요한 마이데이터 허가·동의 절차 범위, 이체 진행 알림의 광고성 정보 해당 여부, 계산 오류 시 면책 문구의 실효성, 전송 버튼을 전자적 의사표시로 볼 때 필요한 인증수단·로그 보존 범위.

이 항목들은 예/아니오로 답할 수 있는 질문으로 정리되어 있으며, 답변 결과에 따라 §4.1의 해당 REQ-FUNC(특히 REQ-FUNC-005, 010, 015, 046, 053)의 구현 방식이 바뀔 수 있다.

## 9. 면책

이 문서는 제품 구현 참고용이며 **법률·세무 자문이 아니다.** 조문 인용은 국가법령정보센터·국세청 등 공개 법령 자료를 기준으로 확인했으나, 규제 해당 여부 판단은 확인된 사실이 아니라 해석이다. 실제 구현 착수 전 §7.6의 확인 사항에 대해 법무·컴플라이언스·연금시스템팀 검토를 거쳐야 한다.

세법은 매년 개정되므로 세율 상수와 감면율은 코드에 하드코딩하지 말고 시행일이 붙은 설정으로 관리한다(REQ-NF-009).
