# AI 협업 대표 사례

> 프롬프트와 Tool Call 전체를 보관하지 않습니다. 제품 판단이나 결과 품질을 바꾼 사례 2~3개만 기록합니다.

## 사례 1 · Goal 1 — 공통 개발 기반

- 목표: 로그인·회원가입(시연용)·홈·공통 라우팅·공통 레이아웃·mock 공통 타입 구현
- AI에게 제공한 근거: `docs/submission/PRD_MVP.md`, `docs/submission/SRS_MVP.md`, [Issue #1](https://github.com/YseungY/pension-plus/issues/1), `docs/team/product/예상_프로토타입.html`, 디자인 시스템
- AI가 제안한 내용: 8개 라우트(로그인·회원가입·홈·기능1 3개·기능2 2개) 구조, SRS §7.2 기반 mock 타입 스키마, 기능1·2 미착수 영역용 Placeholder 컴포넌트
- 사람이 검토·수정·승인한 지점: mock 인증 기준(실제 계정 생성 없음, 시연용 배지 필수) 확정, 로그인·회원가입을 킥오프 문서상 "제외 범위"와 구분해 시연용 UI로만 포함하도록 범위 재확인
- 최종 결과: `npm run build` 성공, `any` 사용 0건, 8개 라우트 전부 200 확인 후 `work/seungyeon`에 커밋·푸시
- 다음에는 바꿀 점: 한 번에 요청하는 화면 범위를 더 작게 나눠서 검토 단위를 짧게 가져갈 필요가 있음

### 사례 2 · 기능1 — 이관 현황판

- 목표: 계좌·종목 확인부터 5단계 이관 진행 현황과 완료 화면까지 이어지는 기능1 구현
- AI에게 제공한 근거: 예상 프로토타입, SRS FR-002~009, 모바일 앱 디자인 시스템, 기능1 Issue #2·#3
- AI가 제안한 내용: 계좌 사전조회·종목 판정·이관 상태를 페이지와 mock 데이터로 분리하고, 현재 단계와 제한 기간을 시각적으로 강조하는 구조
- 사람이 검토·수정·승인한 지점: 기능1 담당 유고은이 모바일 화면의 정보 우선순위와 문구를 확인했고, 통합 담당 양승연이 홈 진입 경로·브라우저 뒤로가기·전체 디자인 일관성을 점검
- 최종 결과: `src/features/transfer`에 진입, 사전조회, 보유 종목, 이관 현황, 완료 흐름을 구현하고 공통 라우터와 연결
- 다음에는 바꿀 점: 정상 상태뿐 아니라 고객 확인 필요·지연 상태를 초기에 함께 검토해 상태별 QA를 더 체계화할 필요가 있음

### 사례 3 · 기능2 — 연금 외 수령 모의계산

- 목표: 인출 희망 금액에 따른 재원별 차감액, 예상 세금, 실수령액을 설명하는 기능2 구현
- AI에게 제공한 근거: 예상 프로토타입, SRS FR-010~012, 원본 SRS 계산 규칙, 기능2 Issue #4·#5
- AI가 제안한 내용: 계산 규칙을 화면과 분리한 순수 함수로 만들고 입력·결과 화면에서 같은 mock 데이터를 사용하도록 구성
- 사람이 검토·수정·승인한 지점: 기능2 담당 김동건이 입력·결과 흐름을 확인했고, 통합 담당 양승연이 계산값·모의계산 고지·실제 거래로 오해할 표현이 없는지 교차 검증
- 최종 결과: `src/features/withdrawal`에 입력·결과 화면과 계산 모듈을 구현했으며 2026-09-03 Vitest 3개가 모두 통과
- 다음에는 바꿀 점: 세율과 인출순서의 정책 근거 버전을 함께 표시해 향후 제도 변경 시 검증 범위를 더 명확히 할 필요가 있음

## 기록 원칙

- AI를 많이 사용했다는 사실보다 어떤 판단에 도움이 됐는지 기록합니다.
- AI 결과를 그대로 채택하지 않고 사람이 확인한 근거와 수정 내용을 남깁니다.
- 최종 구현과 연결되지 않은 긴 대화나 프롬프트 전문은 제출하지 않습니다.
