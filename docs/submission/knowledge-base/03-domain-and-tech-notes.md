# 도메인·기술 메모

## 도메인 원칙

- 완료일은 단일 날짜로 확정하지 않고 예상 기간으로 표시합니다.
- 확인되지 않은 매매 가능 상태는 보수적으로 제한 상태로 표시합니다.
- 인출순서는 사용자가 임의로 선택하는 추천이 아니라 법정 순서에 따른 계산입니다.
- 세금 결과에는 적용 기준과 모의계산 한계를 함께 표시합니다.

## 기술기획의 두 관점

기술기획을 "비즈니스 로직"과 "딜리버리 로직" 두 층으로 나눠서 관리합니다.

### 비즈니스 로직 — 핵심 시나리오를 기능·성능으로 표현

**기능1 · 타사 퇴직연금 가져오기**

```
사용자: 홈 → "타사 퇴직연금 가져오기" 선택
  → 이전 계좌·종목 확인 (그대로 이전 / 매도 후 이전 / 판정 불가 3그룹 판정)
  → 이전 전 제한사항 확인 (이체 불가 조건, 매매 잠금 구간 시작·해제)
  → 이관 조건 최종 확인 → 이관 신청
  → 이관 현황판: 5단계 진행 상태, 확정/추정 구분, 완료일은 기간으로 표시
```

**기능2 · 연금저축 관리(연금 외 수령)**

```
사용자: 홈 → "연금저축 관리" → 출금 관리 → "연금 외 수령" 선택
  → 인출 희망 금액 입력, 연금수령한도 대비 게이지 확인(초과 입력 허용)
  → 법정 3층 인출순서 계산 (과세제외금액 → 이연퇴직소득 → 세액공제분·운용수익)
  → 재원별 차감액·예상 세금·실수령액 확인 + 모의계산 한계 안내
```

각 화살표가 SRS의 FR 하나에 대응합니다(`docs/submission/SRS_MVP.md` 참고). 발표에서는 이 두 시퀀스를 다이어그램으로 확장해 소개합니다.

### 딜리버리 로직 — 화면까지 도달하는 기술적 방법

- FE: Vite + React + TypeScript, Tailwind CSS(디자인 토큰), React Router(클라이언트 라우팅)
- BE: 없음 — 서버·DB·실제 금융 API 미연동. `src/lib/mock-types.ts`의 로컬 TypeScript mock 데이터로 상태를 표현
- 인증: 실제 로그인 없음 — 공동인증서·금융인증서 선택 mock UI로 대체(`/app/connect`)
- 배포: Vercel 정적 호스팅. 하나의 SPA를 `basename` 분기로 `/`(랜딩페이지)와 `/app`(시연 앱) 두 경험으로 서빙하고, `vercel.json`의 catch-all rewrite로 새로고침·직접 진입 시에도 클라이언트 라우팅이 깨지지 않게 함
- 검증: Vitest로 계산 로직 대표값 테스트

## 데이터 사용 원칙

제품 시나리오는 마이데이터 조회가 완료된 상황을 가정하지만 실제 API를 호출하지 않습니다. UI에는 `시연용 데이터`라고 표시하고, 데이터 조회 경계를 분리해 향후 실제 API로 교체할 수 있게 합니다.
