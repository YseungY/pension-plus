Day 1발표자료 작성 시작

프로젝트 한 문장 목표

기획 문서를 작성하는 데서 끝나지 않고, 팀과 AI 에이전트가 같은 근거와 명세를 읽고 제품을 만들 수 있는 상태까지 연결합니다.

AI 네이티브 기획은 AI에게 일을 많이 시키는 방식이 아닙니다. 사람의 목표·근거·제약·결정을 AI가 오해하지 않도록 지식과 명세를 구조화하고, 결과를 사람이 검토·수정·승인할 수 있는 운영체계를 만드는 방식입니다.
STEP 1기획 자산 재사용기존 시장·고객·문제·가치·PRD 결과를 짧게 정리합니다.
STEP 2Knowledge Base근거와 결정을 AI가 탐색할 수 있는 LLM-Wiki 경로로 만듭니다.
STEP 3PRD → SRS제품 의도를 기능·비기능·데이터·상태·검증 명세로 확장합니다.
STEP 4SRS → TASKGitHub Issue와 Project로 실행 단위를 추출하고 관리합니다.
STEP 5Prototype → Deploy핵심 UX를 실제 프로그램으로 구현하고 Vercel에 배포합니다.

1. 프로젝트의 성격

1-1. 앞선 프로젝트의 모든 핵심 경험을 재사용합니다

시장분석, 서비스 기획, 고객 문제 정의, 벤치마킹, 가치 제안, PRD, AI 활용 기록, 체계적 문서화와 의사결정 과정은 새로 반복 작성하지 않습니다. 검증된 핵심 결론과 아직 남은 가정만 압축해 가져와 이번 프로젝트의 입력값으로 사용합니다.

기존 수행 내용이번 프로젝트에서의 재사용 방식새롭게 확장할 내용
시장·세그먼트·고객 분석핵심 근거와 타깃 정의를 KB에 이관추가 리서치 질문과 근거 간 연결
문제 정의·JTBD·가치 제안제품 목표와 핵심 사용자 흐름의 기준으로 사용요구사항 ID와 Acceptance Criteria로 구체화
PRD제품 목적·범위·우선순위의 기준 문서로 유지SRS의 기능·비기능·데이터·상태 명세로 확장
의사결정·AI 활용 기록재사용할 결정과 폐기할 가정을 구분GitHub Issue·Project·에이전틱 목표 관리로 연결
프로토타입 또는 화면 아이디어UX 가설과 핵심 화면 후보로 사용실제 실행·배포 가능한 프로그램으로 제작
재사용 원칙: Copy가 아니라 Curate기존 자료를 전부 복사하지 않습니다. 이번 제품 구현에 필요한 근거·결정·제약만 선별하고, 오래되었거나 충돌하는 내용은 상태를 표시합니다.

1-2. ‘완성 제품 개발’보다 ‘기획에서 개발로 넘어가는 운영체계’를 경험합니다

32시간 안에 전체 기능을 구현하는 것은 목표가 아닙니다. 전체 제품의 요구사항과 개발 TASK는 설계하되, 실제 구현은 핵심 사용자 흐름을 검증할 수 있는 UI & UX 범위로 제한합니다. 이 범위 제한은 미완성이 아니라 올바른 프로젝트 관리입니다.

2. 완주 기준과 범위

2-1. 반드시 완성할 것

  • 기존 기획 근거와 추가 리서치가 연결된 LLM-Wiki형 Knowledge Base
  • 제품 목적에서 구현·검증 기준까지 이어지는 SRS Lite
  • SRS의 요구사항 ID를 참조하는 GitHub Issue와 GitHub Project
  • 핵심 UX TASK만 구현한 실행 가능한 웹 프로토타입
  • Vercel 배포 URL과 커스텀 도메인 연결
  • 기획→명세→TASK→구현의 추적관계와 AI 활용 경험을 설명하는 발표

2-2. 이번 프로젝트에서 하지 않을 것

  • 기존 시장분석·페르소나·CJM·PRD를 처음부터 다시 작성하기
  • 완전한 IEEE 표준 문서 수준의 방대한 SRS 만들기
  • 전체 기능, 완전한 백엔드, 실제 결제·인증·운영 어드민까지 모두 구현하기
  • 많은 AI 에이전트를 동시에 실행했다는 사실 자체를 성과로 제시하기
  • 프로토타입의 시각적 화려함을 위해 요구사항·검증·발표 통합을 희생하기

2-3. 핵심 범위 잠금 규칙

3-2. 제출물 경량화 원칙

  • 스크린샷을 별도 파일로 모으지 않고 Master Deck 또는 README에 삽입합니다.
  • AI 프롬프트 전체 로그를 제출하지 않습니다. 판단을 바꾼 대표 사례 2~3개만 남깁니다.
  • TASK 명세는 별도 문서가 아니라 GitHub Issue 본문이 원본입니다.
  • 로드맵과 진행률 표를 별도 작성하지 않고 GitHub Project View를 사용합니다.
  • 발표자료는 마지막 날 새로 만들지 않고 매일의 통합 결과물로 관리합니다.

5. 빠른 의사결정과 GitHub 작업관리

5-1. 15분 Decision Clock

중요한 선택은 논의를 무기한 늘리지 않고 다음 순서로 처리합니다.

  1. 3분: 무엇을 결정해야 하는지 한 문장으로 고정합니다.
  2. 5분: 후보를 최대 3개로 제한하고 근거·제약을 확인합니다.
  3. 4분: 사용자 가치, 구현 가능성, 근거 수준, 시간 비용을 각각 1~3점으로 빠르게 비교합니다.
  4. 3분: 결정권자가 선택하고, 재검토 조건과 폐기한 이유를 한 줄로 남깁니다.
결정권 규칙되돌리기 쉬운 결정은 해당 Issue 담당자가 결정합니다. 범위·데이터·보안·배포처럼 되돌리기 비싼 결정은 팀 전체가 검토하되, 시간이 끝나면 Product Lead가 현재 근거로 잠급니다.

5-2. Decision Log는 핵심 결정만 기록합니다

5-3. GitHub Project 최소 운영 구조

  • Board: Backlog → Ready → In Progress → Review → Done
  • 필수 필드: Owner, Priority, Requirement ID, Workstream, Target Day
  • 권장 라벨: area:research, area:spec, area:ui, area:ux, area:qa, risk
  • WIP 제한: 팀원 1명당 In Progress Issue 1개
  • 로드맵: Day 1~4를 Iteration 또는 Target Day로 표현

11. LLM-Wiki 방식의 Knowledge Base

11-1. 목적

Knowledge Base는 조사자료 보관함이 아니라, 팀원과 AI가 현재 제품의 근거·용어·결정·미해결 질문을 같은 구조로 탐색하기 위한 작업 경로입니다. 긴 통합 문서 하나보다, 목적별로 나뉜 짧은 문서와 명시적인 링크를 사용합니다.

11-2. 최소 작성 규칙

  • Index First: 00-index.md에서 핵심 문서·질문·Requirement로 이동할 수 있어야 합니다.
  • 한 페이지 한 목적: 제품 맥락, 근거, 기술, 결정, 용어를 섞지 않습니다.
  • 근거 상태: 확인된 사실, 분석적 추론, 아직 검증하지 않은 가정을 구분합니다.
  • 출처와 시점: 외부 자료는 URL·게시일·확인일을 기록합니다.
  • 연결: 주요 결론은 관련 PRD/SRS Requirement ID 또는 Decision ID와 연결합니다.
  • 충돌 보존: 서로 다른 근거가 충돌하면 하나를 조용히 지우지 않고 차이와 최종 판단을 남깁니다.

11-3. KB 항목 템플릿

항목작성 내용
Title / Tags이 페이지의 질문 또는 지식 단위와 검색용 태그
StatusFact / Inference / Assumption / Decision / Open Question
SummaryAI가 짧게 인용할 수 있는 2~4문장 핵심
Evidence원문 링크, 사용자 조사, 화면 관찰, 데이터 등
Implication제품·UX·기술·운영에 미치는 영향
Linked Items관련 KB 문서, Decision ID, Requirement ID, Issue
Updated마지막 갱신일과 담당자

11-4. AI가 KB를 실제로 사용하게 하는 질문

docs/knowledge-base 경로의 문서만 근거로 다음을 수행하세요.
1. 현재 제품 목표와 핵심 사용자 문제를 요약하세요.
2. 답변마다 사용한 KB 문서와 근거 상태를 표시하세요.
3. 근거가 없는 내용은 추정하지 말고 Open Question으로 남기세요.
4. 제안이 기존 Decision 또는 SRS Requirement와 충돌하면 먼저 알려주세요.
KB 완료 기준팀원이 “왜 이 기능이 필요한가?”라고 물었을 때 3분 안에 근거·결정·요구사항을 따라갈 수 있고, AI가 근거 없는 빈칸을 사실처럼 채우지 않도록 문서 경계가 명확해야 합니다.

13. SDD와 비개발자 PM의 기술 학습 계획

13-1. 이번 프로젝트의 SDD

SDD(Spec Driven Development)는 구현 전에 모든 것을 완벽하게 예측하는 방식이 아닙니다. 명세를 개발의 기준점으로 두고, 구현 중 발견된 사실을 명세와 TASK에 되돌려 반영하는 반복 운영 방식입니다.

S0Intent제품 목표와 범위를 잠급니다.
S1Requirement기능·제약·검증 조건을 씁니다.
S2Issue Ready독립 실행 가능한 TASK로 나눕니다.
S3Build & Verify구현하고 Acceptance Criteria로 검증합니다.
LOOPSpec Update발견·변경을 SRS와 KB에 되돌립니다.

13-2. 기술을 전부 배우지 말고, 현재 결정을 이해할 만큼 빠르게 학습합니다

비개발자 PM에게 필요한 것은 4일 안에 개발자로 전환되는 것이 아니라, 선택한 기술이 제품 요구사항에 어떤 가능성과 제약을 만드는지 이해하고 AI가 만든 결과를 검토하는 경험입니다. 학습 주제는 최대 3개, 각 주제는 30~60분으로 제한합니다.

학습 질문제품 결정과의 연결작은 실습완료 증거
Next.js의 Server/Client Component 차이는 무엇인가?상호작용 UI와 데이터 처리 위치 결정한 컴포넌트의 경계 변경선택 이유와 제약 3줄
Mock Data와 실제 API 연동 경계는 어떻게 나누는가?프로토타입과 향후 제품 개발의 연결Repository/Adapter 인터페이스 만들기교체 지점 설명
Vercel 환경변수와 공개 변수의 차이는 무엇인가?비밀키 노출 방지와 배포 운영샘플 환경변수 연결노출 금지 항목 체크

  • 채택 기술: 무엇을 사용하며 어떤 Requirement를 위해 선택했는가?

Goal Setup/goal-setting으로 목표, 입력 명세, 범위 밖, Done, 검증, 중단 조건을 고정15~25분Goal이 Issue·Requirement와 연결되는가?
Cycle 1/goal로 공통 기반 또는 첫 Happy Path를 구현45~60분중간 결과, 명세 이탈, 실행 가능 여부
Cycle 2/goal로 상위 결함·핵심 예외를 수정40~60분Acceptance Criteria와 회귀 위험
최소 기록만 남깁니다.각 Cycle마다 목표, 에이전트에게 준 근거, 사람이 개입한 지점, 최종 결과, 다음에 바꿀 점을 1~2문장씩 기록합니다. 프롬프트 전문이나 모든 Tool Call을 제출할 필요는 없습니다.

14-4. AI 활용 원칙

  • AI에게 저장소 전체를 반복해서 읽히기보다 KB Index와 관련 SRS·Issue를 지정합니다.
  • 리서치·명세·구현·리뷰 역할을 구분하고, 같은 에이전트의 자기검증만으로 Done 처리하지 않습니다.
  • 외부 사실, 라이브러리 버전, 배포 설정은 공식 문서 또는 실제 실행 결과로 확인합니다.
  • 개인정보·비밀키·실제 고객 데이터·사내 기밀을 프롬프트와 저장소에 넣지 않습니다.
  • AI가 생성한 코드의 출처·라이선스·보안·접근성 책임은 팀이 검토합니다.

15. UI & UX 프로토타입과 Vercel 배포

15-1. UI & UX TASK를 먼저 추출하는 이유

전체 TASK 중 area:ui와 area:ux를 필터링하면, 실제 제품 개발 이전에 사용자 흐름·정보 구조·상태·설명 방식의 품질을 검증할 수 있습니다. 프로토타입은 별도의 일회성 그림이 아니라 향후 실제 프로그램으로 확장할 수 있는 코드 기반 초기 제품으로 만듭니다.

15-2. 구현 수준

필수조건부이번 범위 밖
핵심 Happy Path, 실제 클릭·입력·상태 변화, 일관된 디자인, 반응형 핵심 화면, Mock Data, 1~2개 예외 상태간단한 로컬 저장, 공개 API, Supabase 등 — 핵심 UX 검증에 필요하고 시간 내 가능한 경우실제 결제, 실사용자 인증, 민감정보 처리, 완전한 관리자 기능, 고가용성 인프라, 전체 백엔드

15-3. Vercel·커스텀 도메인 운영 순서

  1. DAY 2까지 저장소가 로컬에서 정상 실행되는지 확인합니다.
  2. DAY 3 15:50 전 Preview 배포를 완료하고 팀 외부에서 URL 접속을 확인합니다.
  3. DAY 3에 커스텀 도메인 연결을 시작해 DNS 전파 대기시간을 확보합니다.
  4. DAY 4에 Production 배포, HTTPS, 환경변수, 모바일 접속, 새로고침 경로를 확인합니다.
  5. 도메인 전파가 늦어질 경우 Vercel 기본 URL을 데모 백업으로 준비하고 연결 상태를 기록합니다.

15-4. Prototype Definition of Done

  • README의 실행 방법으로 다른 팀원이 로컬 실행할 수 있다.
  • 핵심 사용자가 시작부터 목표 달성까지 중단 없이 이동할 수 있다.
  • 구현된 기능이 SRS Requirement와 GitHub Issue에 연결된다.
  • 모바일과 데스크톱의 핵심 레이아웃이 깨지지 않는다.
  • 중요한 Loading·Empty·Error 상태 중 필요한 것을 설명하거나 구현했다.
  • 비밀키·개인정보·운영 데이터가 코드와 배포물에 포함되지 않았다.
  • Vercel Production URL과 커스텀 도메인 또는 연결 상태를 확인했다.

17. 최종 제출 체크리스트

내용·명세

  • 기존 프로젝트 결과의 재사용·폐기·추가확인 기준이 보인다.
  • KB Index에서 근거·결정·용어·Open Question을 탐색할 수 있다.
  • PRD의 제품 목표가 SRS Requirement와 모순되지 않는다.
  • 핵심 Requirement가 GitHub Issue와 Prototype에 연결된다.

프로젝트 운영

  • GitHub Project에서 Backlog·진행·검토·완료 상태와 담당자를 확인할 수 있다.
  • 핵심 결정의 근거와 재검토 조건이 남아 있다.
  • 기술 학습 주제가 실제 제품·코드·배포 결정에 적용되었다.
  • AI 활용에서 사람의 승인·수정·검증 지점을 설명할 수 있다.

프로토타입·배포·발표

  • 핵심 Happy Path가 실제로 작동하며 2분 이내 시연할 수 있다.
  • Vercel Production URL과 커스텀 도메인 또는 연결 상태가 확인된다.
  • README에서 Master Deck, GitHub Project, 문서, 배포 URL을 모두 찾을 수 있다.
  • Master Deck 12~16p와 데모 백업이 준비되었다.
  • 최종 제출은 Master Deck·GitHub Workspace·배포 URL의 3개 링크로 정리했다.
