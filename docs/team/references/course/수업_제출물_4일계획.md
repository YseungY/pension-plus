## 4. Scope 잠금

### 핵심 사용자

팀 회의에서 1명을 확정한다.

### 핵심 Happy Path

기능1 `이전 조건 확인 → 모의 이관 시작 → 진행 현황 확인`을 중심 흐름으로 추천한다.

### 보조 흐름

기능2 `인출금액 입력 → 차감 순서·세금·실수령액 확인`을 보조 흐름으로 구현한다.

### 중요 예외

다음 중 1~2개만 선택한다.

- 고객 확인 필요
- 인출금액이 평가금액을 초과한 경우
- 연금수령한도 초과

### 범위 제한

- 기능 요구사항: 8~15개
- 구현 Issue: 4~8개
- 기술 학습 주제: 최대 3개
- 실제 인증·금융기관 API·민감정보 처리: 제외
- 새 기능을 추가하려면 같은 크기의 기존 기능을 제외

## 5. SRS Lite 작성 계획

기존 `PRD_연금플러스_최종.md`의 요구사항·상태·계산·Acceptance Criteria를 재사용한다.

### 필수 내용

1. 목적과 범위
2. Out of Scope
3. 사용자와 핵심 흐름
4. 기능 요구사항 `FR-001` 형식
5. UI 요구사항 `UI-001` 형식
6. 비기능 요구사항 `NFR-001` 형식
7. 데이터와 상태
8. 예외와 복구
9. Acceptance Criteria
10. 가정과 Open Questions
11. 요구사항 추적표

### 요구사항 작성 기준

각 요구사항에는 다음만 작성한다.

- ID
- Requirement
- Rationale
- Input / Rule / Output
- Acceptance Criteria
- Source
- Priority

SRS를 완벽하게 만든 뒤 개발을 시작하지 않는다. 핵심 흐름의 요구사항이 Issue로 만들 수 있는 상태가 되면 구현을 병행한다.

## 6. 기술 학습 주제

다음 세 가지를 추천한다.

1. React에서 URL·컴포넌트·상태가 어떻게 연결되는가?
2. Mock Data와 향후 실제 API의 경계를 어떻게 나누는가?
3. Vercel Preview·Production 배포와 환경변수는 어떻게 작동하는가?

각 주제는 다음 네 줄로 기록한다.

- 왜 필요한가?
- 어디에 적용했는가?
- 무엇을 확인했는가?
- 남은 한계는 무엇인가?

## 8. 4일 일정

### 운영 원칙

- 기능 구현을 최우선으로 한다.
- 문서가 완성될 때까지 개발을 기다리지 않는다.
- 개발 전에 필요한 최소 기준만 정한다: 핵심 사용자, 흐름, 요구사항 ID, 완료 조건.
- 구현 중 발견한 변경사항은 매일 마지막 30분에 SRS와 Issue에 반영한다.
- Day 2까지 핵심 흐름을 완성하고 Preview 배포하는 것을 목표로 한다.

### Day 1 · 08.31 — 최소 명세·개발 시작

- 대표 사용자와 핵심 Happy Path 확정
- 핵심 요구사항과 완료 조건만 우선 확정
- Vite 프로젝트와 공통 개발환경 구성
- 기능1·기능2 화면 구현 시작
- GitHub Issue를 핵심 구현 단위로 먼저 생성
- KB·SRS는 목차와 ID만 생성

#### 종료 기준

- 로컬에서 앱이 실행된다.
- 최소 한 개의 핵심 화면이 작동한다.
- 구현 중인 작업이 Requirement ID와 Issue에 연결돼 있다.

### Day 2 · 09.01 — 핵심 흐름 완성·Preview

- 기능1 핵심 Happy Path 완성
- 기능2 입력·계산·결과 연결
- 공통 디자인 토큰과 모바일 레이아웃 적용
- 핵심 계산 테스트
- Vercel Preview 1차 배포
- 구현이 끝난 요구사항의 Acceptance Criteria 보완

#### 종료 기준

- 핵심 Happy Path를 처음부터 끝까지 실행할 수 있다.
- 기능2 대표 계산값이 맞는다.
- 외부에서 Preview URL을 열 수 있다.

### Day 3 · 09.02 — 예외·QA·제출 문서 보완

- 필요한 예외 1~2개 구현
- 모바일·데스크톱·새로고침 QA
- 사용자 테스트와 중요한 오류 수정
- 기존 자료를 Knowledge Base로 짧게 정리
- SRS Lite 8~15개 요구사항 완성
- Requirement→Issue→구현 추적표 작성
- Master Deck에 실제 구현 화면 반영

#### 종료 기준

- 핵심 기능과 예외가 Preview에서 작동한다.
- SRS·Issue·구현 연결을 확인할 수 있다.
- 발표에 사용할 실제 화면이 준비됐다.

### Day 4 · 09.03 — 검증·Production·제출

- 요구사항 추적관계 최종 확인
- 치명적인 오류와 계산 오류 수정
- Vercel Production 배포
- README에 모든 제출 링크 연결
- Master Deck과 데모 영상 완성
- 3개 링크 최종 확인

#### 종료 기준

- Master Deck URL이 있다.
- GitHub Workspace에서 모든 근거를 찾을 수 있다.
- Production URL에서 핵심 흐름이 작동한다.

## 9. GitHub Issue 최소 구성

다음 6개 Issue를 기본안으로 사용한다.

1. `[공통] Vite·라우팅·디자인 토큰 구성`
2. `[기능1] 이전 계좌·종목 판정 화면`
3. `[기능1] 이관 현황판·상태 전환`
4. `[기능2] 인출 조건 입력·한도 게이지`
5. `[기능2] 3단계 차감·세금 결과`
6. `[배포] QA·Vercel Production·README 연결`

각 Issue에는 연결 Requirement, 포함·제외 범위, Acceptance Criteria, 확인 방법을 적는다.
