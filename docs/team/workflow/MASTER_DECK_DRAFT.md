## 2~3 · 기존 분석의 사용자·문제·시장 근거와 이번 Scope (DAY 1)

**핵심 사용자** — PB 도움 없이 연금계좌 이전을 직접 확인해야 하는 일반 고객

**문제** — 지금 처리 단계와 매매 제한 기간을 알 방법이 없다

> KB증권 실제 화면 확인 결과, 처리 상태가 "신청중" 한 줄로만 표시됨. 여기서 프로젝트가 출발했습니다.

**기존 기획 자산 재사용**

| 구분 | 내용 |
|---|---|
| 재사용 | 상세 PRD (66개 요구사항 · 12화면), 서비스 역기획서, 디자인 시스템 |
| 이번 Scope로 축소 | 요구사항 66개 → **12개**, 화면 12개 → **6개** |
| 제외 | 기능3(한도 계산기 단독), 로그인·인증·DB·실제 금융 API |

**MVP 6화면**
홈 · 이전 계좌·종목 확인 · 이전 전 제한사항 확인 · 이관 현황판 · 인출 조건 입력 · 인출 결과

## 4 · Knowledge Base 구조와 핵심 추가 리서치 (DAY 1)

지식베이스 5종: 제품맥락 · 리서치근거 · 도메인·기술메모 · 의사결정기록 · 용어집

**핵심 근거 3개**

1. 기존 화면은 처리 상태를 한 줄로만 표시 → 기능1은 단계별 현황과 다음 행동을 함께 보여준다
2. 인출 재원은 법정 순서(3층)로 강제 차감된다 → 기능2는 자유 추천이 아닌 결정론적 모의계산으로 설계
3. 실제 API·민감정보 처리는 4일 MVP엔 과도하다 → 로컬 시연용 데이터로 대체

## 5~6 · PRD 핵심 목표와 SRS 주요 Requirement·예외·비기능 조건 (DAY 2)

**PRD 핵심 목표**

- 핵심 Happy Path: 연동된 연금계좌 선택 → 보유 종목 확인 → 이전 시 제한 사항 확인 → 이관 조건 최종 확인 → 단계별 진행 현황 확인
- 보조 흐름: 인출 조건 입력 → 법정 차감 순서·예상 세금·실수령액 확인

**SRS 주요 Requirement**

- Requirement **12개**(FR-001~012), MVP 화면 6개에 전부 매핑
- 중요 예외 2개: 고객 확인 필요 상태 / 인출금액이 평가금액을 초과한 경우
- 비기능: 모바일 360px 우선, `시연용 데이터`·`모의계산` 명시, 확정/추정 정보 시각적 구분
